What the trace can and cannot tell you

  • Two blocks side by side on one lane is a real serial cost. Two blocks overlapping across lanes is not free on this machine. Concurrent SSD traffic and GPU work contend for one memory controller, measured three ways: early submit -8.2%, warm prefetch -15.4%, shared read buffer neutral with the saving taken back by the GPU drain.
  • Only two blocks have no upstream dependency. ngram_wait needs the input IDs, known at token start. shared_expert needs the layer input, not the routed experts. Everything else is a true chain: the route needs the GPU, the bytes need the route, the MoE needs the bytes, the next layer needs the MoE.
  • Both free blocks were already tried. Issuing the n-gram reads early gained 1.5%, inside noise. Overlapping the shared expert measured 2.59 against 2.68 tok/s.
  • Blocks are per-token totals across all 48 layers. The inspector gives the per-layer figure and the call count.
  • score_sync and router_sync are not stages. Each is the main thread blocked at an mx.eval, so it holds whatever GPU work was still outstanding at that moment, and it shrinks when the host does more work in front of it. Subtracting measured components from either one prices scheduling, not a missing stage. Five candidates for the difference were measured and none of them is it: the layer glue is 1.56 ms, distinct layers cost 0.93x a repeated one, page faults during the drain are 0.00 MB, the mask and renormalisation together are 1.36 ms, and the write pattern is -0.3%.
  • That last one settles an open question in the research log, which blamed the shared read buffer's absorbed saving on 16 workers scattering writes where the concatenate copied sequentially, and said the GPU might read memory in a different coherency state. Measured on the same bytes and the same kernel: 99.8 GB/s concatenated against 100.1 GB/s scattered, byte-identical. The write pattern does not matter and that explanation can be withdrawn.
  • Splitting every eval into async_eval then eval separates CPU-side scheduling from waiting. Scheduling is 14 ms per token across 98 calls, about 143 us each. The remaining 151 to 156 ms is the main thread waiting after Metal already holds the work, while the GPU counter reports 26 ms of shader time.
  • The idle window will accept real work, within limits that were measured rather than assumed. 12,288 extra graph nodes per token are free. Arithmetic is free to about 5.4 GFLOP per token: a 384x384 matmul in every layer cost +0.1 ms across three alternating passes. Memory is not free. A 640 MB resident bank cost +71 MB per token of extra expert reads and +39 ms, because every byte it holds is a byte the page cache cannot use.
  • Corrected. Earlier versions of this page put the GPU at about 9% busy and called the remainder not work. That came from the IOKit Device Utilization % counter, which a Metal System Trace shows undercounts by 3.2x. Measured by Instruments over 16,554 intervals, the GPU is busy 12,278 ms of a 44,306 ms span, which is 27.7%, or about 149 ms per token. Two independent estimates predicted that factor before the trace existed: an injected-matmul sweep fitted 2.9x, and a saturating matmul calibration read 32% where it should approach 100.
  • A token is now fully accounted: roughly 257 ms of drive, 149 ms of real GPU compute, 14 ms of CPU-side scheduling, 4 ms of host bookkeeping, and the rest CPU to GPU submission latency. Nothing in it is unexplained, and nothing in it is obviously removable.
