# Work log: 2026-08-21 to 2026-08-24

This log records the work after the original V3 Compact build.
It separates measured results from ideas and incomplete work.

## 1. Goal

The main goal was faster repository ingestion without lower coding quality.
The practical target was 80 to 100 prompt tokens per second on one 16 GB Mac.

The secondary goal was a useful local coding agent.
It needed repository tools, file edits, saved settings, and clear terminal output.

## 2. Model lineage

The existing E2 and GGUF models already came from the original BF16 model.
Further distillation between those children did not add missing source information.

The V3.1 Compact model remained the quality baseline.
It uses activation-aware heterogeneous affine quantization in MLX.
It protects sensitive full-attention weights and late MLP down projections.

The local model is about 9 GB and has 64 layers.
Its weights use 2-bit, 3-bit, and 4-bit groups with group size 128.

## 3. Terminal chat

The terminal evolved from a simple chat into a local coding agent.

Added capabilities:

- workspace selection
- directory and file discovery
- source search
- file reads
- file writes and text replacement
- local command execution
- optional change approval
- live answer streaming
- gray reasoning text
- animated ingestion status
- `Ctrl+C` reply cancellation without session loss
- named session save and load
- persistent operator settings

The model stays loaded between turns. The engine appends new tokens to existing state.
This prevents full conversation reprocessing on each turn.

## 4. Reasoning and tool failures

Several model failures appeared during real repository tasks:

- repeated identical tool calls
- incomplete tool calls
- missing `path` parameters
- long reasoning without a useful answer
- reasoning that resumed after a forced answer
- literal tool XML printed as plain text
- weak behavior at low effort

The terminal added repair and control logic:

- detect identical tool calls
- block loops after repeated calls
- repair safe missing parameters
- direct the model to conclude after a stall
- audit severe claims before edits
- request a final answer after tool limits

Hard token limits made some answers worse.
The model often stopped mid-thought and produced another incomplete continuation.
The final design uses state and behavior guards instead of repeated blind continuation.

## 5. Approval and workspace persistence

The first approval parser could display `y` and still record a denial.
Terminal control characters changed the exact input value.

The parser now removes control characters and normalizes the answer.
It accepts English and Portuguese approval forms.

Workspace changes also failed to persist at first.
The terminal now saves the workspace with other options in:

```text
~/.frankenstein/preferences.json
```

## 6. Internet search

The terminal gained a small web-search tool through Tavily.

The adapter returns a short answer and at most three results.
It limits each excerpt and excludes raw page content.
This reduces prompt size and lowers the risk from page instructions.

The feature requires `TAVILY_API_KEY`.

## 7. Model-off tokenization

A repository tokenizer cache was created in `repo_token_cache.py`.
It watches file size and nanosecond modification time.
It hashes and tokenizes only changed files.

The cache uses compressed token IDs in SQLite.
It stays outside the repository to avoid source-tree growth.

Default location:

```text
~/Library/Application Support/QwenRepoCache
```

This solved repeated CPU tokenization work.
It did not solve neural ingestion.

The model must still run every token through all 64 layers.
Pretokenized IDs cannot replace those matrix operations.

## 8. Query-aware source selection

`speculative_prefill.py` selects relevant source blocks before neural prefill.
It understands basic source structure and request terms.

The current defaults allow 2,048 selected tokens and 24 blocks.
Query-aware selection improves apparent ingestion by reducing the input.
It can omit relevant context, so it is not exact full-file processing.

## 9. Exact context images

The project implemented exact saved neural context in `repo_context_image.py`.
The saved state contains attention KV and recurrent Gated-DeltaNet state.

Paired in-process measurement on V3.1:

```text
source tokens       2377
cold prefill        52.38 s
context restore      0.27 s
speed ratio        190.8x
```

The restored state matched normal prefill exactly.

The storage cost is large.
A 1,208-token source required 188.6 MiB.
The practical floor was about 160 MiB for one image.

Context images only work for unchanged, previously processed content.
They bind to model and prompt configuration.
Independent images do not compose into arbitrary new prompt order.

## 10. Dense prefill ceiling

Profiling identified the actual prefill cost.

For a 256-token block:

```text
MLP                         about 67%
Gated-DeltaNet projections  about 16%
attention                   about  8%
recurrent scan              about  2.5%
other                       about  6%
```

Quantized matrix multiplication consumes about 87 percent of total time.
All measured bit widths reached about 2.39 to 2.45 TFLOPS.
Dense BF16 reached about 2.68 TFLOPS.

The best measured tile layout was already in use.
The theoretical estimate was about 48 prompt tokens per second.
The measured sustained result was about 46.8 tokens per second.

This closed the dense-kernel path for the current hardware and model shape.

## 11. Sparse MLP experiment

The sparse design divided each dense MLP into 40 shared groups and 8 optional experts.
Each expert contained 12 groups. The router selected two experts.

Active MLP width was 47.1 percent.

Measured isolated prefill:

```text
dense MLP     54.988 ms
sparse MLP    29.214 ms
speed ratio    1.882x
```

Quality did not pass.
The best Sparse LoRA result had 11.7 percent RMSE and cosine similarity 0.9945.
Many layers had 17 to 25 percent error after one expert was skipped.

End-to-end tests passed two of three simple checks.
The model then entered reasoning and tool loops.

Sparse prefill and sparse generation remain disabled by default.

## 12. Neural Engine experiment

The project tested concurrent GPU and Neural Engine work.
The measured overlap was 88.8 percent.

One quantized Qwen MLP layer had:

```text
relative RMSE    0.00708
cosine           0.99998
package size     135.5 MB
```

Two resident layers reached 1.460 times speed.
Four layers in one multifunction package held about 1.450 times speed.

Eight layers required about 1.1 GB and fell to 0.364 times speed.
Separate four-model execution also fell to 0.377 times speed.

The practical resident limit was between 542 MB and 1.1 GB.
All 64 layers would require about 8.7 GB of Core ML packages.

The ANE method worked for a few layers but could not scale to the full model.

## 13. Whittle MoE evaluation

The project then evaluated an existing post-trained MoE model:

```text

```

The model keeps all 64 attention and Gated-DeltaNet layers.
It changes the dense FFN into shared and routed sections.

The routed layout uses 64 experts with 192 channels each.
It also keeps 5,120 shared channels.
The router activates 16 experts.
The active width is 8,192 channels.

Whittle v2.1 includes post-training.
Its structured tool behavior still remained weaker than V3.1.

## 15. Direct GGUF integration

The first GGUF integration used `llama-server`.
We rejected this path because it added about 450 MB of overhead.
Its terminal animation also overwrote visible model output.

The project then installed `llama-cpp-python` with Metal support.
The official Metal wheel failed repeated CRC checks in one CMake file.
The package was compiled successfully from official source with `GGML_METAL=ON`.

`llama_cpp_engine.py` now loads `libllama` inside the chat process.
It does not use HTTP, a background server, or an open network port.

`chat_whittle.sh` provides a direct experimental launcher.
`chat.sh --whittle` selects the same backend.

## 16. Whittle speed observations

These were interactive observations, not controlled benchmark results.

```text
micro-batch 128   prompt 16.7 tok/s   generation 5.9 tok/s
micro-batch 256   prompt 30-32 tok/s  generation 5.4-5.9 tok/s
```

Free memory was about 0.6 to 0.9 GB during these runs.
The current context limit is 8,000 tokens.

Whittle did not improve ingestion over the V3.1 dense MLX path.
Its larger local footprint also reduced memory headroom.

## 17. Whittle behavior controls

Low effort originally disabled reasoning completely.
The model then produced empty output or repeated directory calls.

The GGUF low-effort mode now keeps a short internal reasoning phase.
After three repeated calls, the next generation hides tool definitions.
It directs the model to give a final answer.

These changes still need a clean regression test.

## 19. Quality improvement plan

A future behavior-training plan was prepared:

1. Create 100 to 300 real repository tasks.
2. Compare V3.1, E2, and GGUF on identical tasks.
3. Save concise successful traces.
4. Add explicit effort-level examples.
5. Train a small LoRA on final layers.
6. Train tool selection, stopping, and no-op behavior.
7. Use failed V3.1 traces as negative examples.
8. Validate on unseen repositories.
9. Merge only after E2 quality parity.
10. Resume sparse training only after behavior stabilizes.

No completed LoRA training is recorded in this period.

## 20. Current conclusion

V3.1 remains the final quality model.
Whittle remains a memory and behavior experiment.

The exact fast path is context-state restoration.
The general fast path is smaller query-aware input.

Dense, exact, cold ingestion remains near 47 tokens per second on this Mac.
No tested method reached 80 to 100 tokens per second with equal quality.
