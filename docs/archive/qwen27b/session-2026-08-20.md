## 2. Measured prefill and decode limits

The main result is that prefill and decode have different limits.

### Prefill is compute bound

```text
dense bf16 matmul, MLP shapes    2.60 - 2.68 TFLOPS
q2 q3 q4 q6 q8, any group size   2.39 - 2.45 TFLOPS   (all identical)
fp32                             2.16 TFLOPS          (20% slower)
27B params x 2 FLOP = 54 GFLOP per token
2.68 TFLOPS / 54 GFLOP = 49.6 tok/s ceiling
measured 46 - 47 tok/s = 93% of ceiling
```

Where the time goes, per 256-token chunk:

```text
GDN layer (incl MLP)   83.47 ms  x48 = 4007 ms
attention layer        83.68 ms  x16 = 1339 ms
MLP alone              55.90 ms  x64 = 3578 ms   <- 67% of everything
```

The MLP dominates. The Gated DeltaNet recurrence is not the bottleneck.

### Decode is bandwidth bound

```text
weights read per token   10.74 GB
M4 bandwidth             about 120 GB/s
ceiling                  11.2 tok/s
measured                 8.5 tok/s = 76%
```

Faster decode requires fewer bytes read per token. Other tested changes do not change this limit.

## 3. Ideas measured and rejected

Do not spend time on these again.

```text
requantising the MLP        every bit width gives the same TFLOPS
fp16 instead of bf16        identical; fp32 is 20% slower
bigger prefill chunks       256 and 1024 give the same throughput
lm_head last token only     no gain: MLX is lazy and already skips it
                            during prefill, peak memory byte-identical
mx.set_cache_limit          the pool holds only 0.03 - 0.29 GB, and
                            capping it low measurably slows decode
removing image/video         already absent; zero vision weights on disk
```

## 4. Memory

### Recovered memory

```text
prefill-step-size 1024 -> 256    peak 12.93 -> 12.10 GB, no throughput cost
paged KV at 256K                 17.18 GB -> 0.81 GB resident
```

Correction to an earlier note in this session: step 256 was reported as 19% slower. That was thermal drift, not the
setting.

### The floor

```text
weights           10.74 GB
runtime overhead   0.55 GB
transients         0.63 GB
------------------------------
resident          about 11.9 GB peak
```

With quality frozen this cannot go lower. On a 17.18 GB machine that leaves about 5 GB for macOS and applications, and
in practice roughly 1 GB free while the machine is in use. This is why other apps suffer, and it is the real constraint,
not the KV.

## 5. Paged KV and sparse selection

See PROJECT.md 47, 48 and 50 for detail. Headline numbers:

```text
exact online-softmax merge      32/32 identical tokens vs contiguous
top-k selection at 8K           8/8 identical tokens, 75% of KV skipped
256K component test             0.81 GB resident, 2.37 ms per layer
needle retrieval, dense         FOUND
needle retrieval, sparse k=4    FOUND, 80% of pages skipped
```

Three changes made sparse execution faster:

```text
preallocated pages       no mx.concatenate per decode step
cached stable gather     concatenate once per selection refresh
two-chunk merge          stable gather + growing page, not one per page
```

Decode attention per layer:

```text
ctx    8192   32 pages  dense  3.78 ms   sparse 1.02 ms
ctx   32768  128 pages  dense  8.43 ms   sparse 1.02 ms
ctx  131072  512 pages  dense 33.10 ms   sparse 1.79 ms
ctx  262144 1024 pages                   sparse 2.37 ms
```

The min/max page bound is loose on random noise and sharp on real attention. A synthetic needle test fails where the
real model succeeds. Never validate selection on random keys.

## 6. Harness memory failures

All were in the harness, none in the paging design.

```text
paged loop running during prefill      built 24 float32 score tensors of
                                       [1,4,6,3000,page] in one lazy graph
unchunked prefill                      kept 64 layers of activations alive,
                                       peak 14.32 GB, 180 s, machine swapped
missing mx.clear_cache in prefill      pool grew without bound
launching with 3.48 GB free            the model needs 11.25 GB
```

Guards added: `paged_kv.py` and `frankenstein_engine.py` now abort unless 8 GB is free. Prefill is chunked and evaluated
between chunks. The page loop only runs at decode.
Any direct `model(...)` call needs `wired_limit` and chunked prefill. Only `stream_generate` applies both automatically.

## 7. Measurement discipline

The machine is fanless. The same context and KV format across three consecutive runs gave:

```text
8.20, 7.20, 5.19 tok/s
```

Therefore timing comparisons across separate runs are invalid. Interleave configurations inside one process and take
medians. Deterministic values such as MLX peak memory stay reliable.
Two conclusions in this session were invalidated by this effect before being caught: fp16 versus Q4 decode, and the
prefill-step throughput cost.

## 8. Terminal chat

`frankenstein_chat.py` starts through `chat.sh`. It reads repositories through bounded tools.
Bugs fixed:

```text
/read raised NameError on the first action
/effort did nothing after the first turn: reasoning_effort only reaches
  the model through the system block, which is written to the KV once.
  The effort instruction now rides on every request turn.

Ctrl+C killed the whole session instead of stopping the reply

  and looped; the range is now optional
```

## 10. Revised target

256K is arithmetically reachable but assumes a dedicated machine, and its prefill costs about 2.4 hours. The target is
now **32-64K**, which leaves a comfortable margin while the Mac is in use. See PROJECT.md 52.

## 11. Open, in order of expected value

```text
1. speculative decoding by prompt lookup
   decode is bandwidth bound, so verifying several drafted tokens in one
   forward pass is the only large win. Output is mathematically identical,
   so quality is untouched. Prompt lookup needs no draft model and no
   extra memory, and code answers quote the context heavily.
   Expected: 8.5 -> about 17 tok/s.

2. prune the vocabulary
   embed_tokens and lm_head are 0.64 GB each for 248320 tokens. lm_head is
   a full matmul per decoded token, 6% of the bytes read. Cutting to about
   120K returns 0.66 GB of RAM and roughly 3% of decode. Safe if every
   single-byte token is kept: rare words become more tokens.

3. persistent prefix cache
   the system block and tool contract are about 800 tokens reprocessed on
   every start, roughly 17 s. The page store can already write them.

4. small companion model
   navigation turns do not need 27B. The same model could serve as the
   speculative draft. Blocked: no small Qwen3.8 with the 248320 vocabulary
   exists locally.

5. quality gate at aggressive selection
   proven at 4 of 20 pages. The 256K claim needs 32 of 1024.

6. min_p sampling instead of greedy plus repetition penalty
```

## 12. Model quality

E2 was not touched and stays frozen. Observed behaviour during the session:

```text
read main.swift and summarised it correctly
raised a hypothesis about a typo'd flag, checked it against the source,
  and withdrew it
identified top-level await and actor isolation concerns
self-corrected a wrong tool parameter name in one turn
```

One failure mode reproduced: with temperature 0 and no penalty it fell into a verbatim repetition loop while reasoning.
A repetition penalty of 1.05 with a 128-token window removed it. A loop guard and a forced `</think>` closure recover
the turn for 3 tokens when reasoning overruns.
