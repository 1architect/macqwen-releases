## Current result on 2026-08-30

The accepted baseline is the complete interactive command below:

```bash
./chat.sh --model flashnext --exact-quality
```

Two changes were accepted on 2026-08-30. Both preserve greedy token IDs and
both were measured through the complete chat path.

| Change | Effect | Scope |
|---|---|---|
| release the MLX allocator after a large prefill | decode +74.0%, tail +50.2% | prompts above 2,048 tokens |
| pin 32 resident experts by default | tail +4.4%, run-to-run spread 12% to 1.7% | all prompts, needs free RAM |

`--threshold 1.0` no longer runs at 0.55 tok/s. The measured tail was 2.073 t/s
against 2.510 for the 0.85 default, both with 32 pinned experts: full routing
costs 17.4%, not 4x, and 20.3% with thinking on. Output differs but neither
is degraded. On a staggered two-train arithmetic problem both settings reach
the same correct answer, 11:13:20, by the same method; full routing adds a
redundant algebraic cross-check and 0.85 restates the problem instead. The
terse reasoning register is identical at both, so the approximation is not a
quality problem and is not what makes the model's thinking read tersely. Until 2026-08-30 the comparison was impossible: `--threshold`
was discarded by every quality profile, and at 1.0 the route observer never
ran so nothing was pinned.

Generated content changes throughput by about 23%. Quote a
rate only with the prompt style attached. Measured serially on a quiet machine,
one instance, thinking off, 32 resident experts:

| Prompt style | Tail | Experts/layer | Pinned |
|---|---:|---:|---:|
| focused technical explanation | 2.435 t/s | 7.92 | 4.46 GB |
| open-ended, "just keep talking" | 1.984 t/s | 7.95 | 4.83 GB |

Same expert count per layer, and the open-ended run pins *more* yet runs
slower. Focused text keeps returning to the same specialists; open-ended text
drifts across the bank, so the 8-token warmup cannot capture its working set
and the page cache covers less of it.

An earlier draft of this section quoted 2.58 tok/s as the steady state. That
came from repeated identical focused prompts and is not representative. Expect
2.0 to 2.4 tok/s depending on content.

The runtime does not reach the 3 tok/s exact-quality target. Every code-side
route to it has been measured and closed. See "All four routes, closed" below,
and `RESEARCH.md` for the evidence. The remaining lever is a lower-bit checkpoint,
which is a storage and quality decision rather than an engineering one.

Two instances in parallel reach 1.52x aggregate throughput with identical
output. That helps batch work, not a single conversation, and it competes with
pinning for RAM.

The acceptance rule required a complete-chat gain with the same prompt, token
IDs, and comparable cache state.

## Upstream RMSNorm bug

`mlx_vlm/models/qwen4_exp/language.py`, `Qwen4ExpRMSNorm.__call__` applies
`y * (1.0 + weight)`, commented as "checkpoint weights are centered at zero".
They are not. Every norm family in the checkpoint has a positive minimum
(`hc_norm` mean +3.75, `q_norm` mean +1.36, `norm_conv` mean +0.89), where a
zero-centered tensor would be half negative. The `1.0 +` doubles every norm's
gain. It yields no NaN and no overflow, so the model looks healthy layer by layer
and emits fluent nonsense. With the fix, "The capital of France is"
returns " Paris" at 44.4%; without it, punctuation at 3.2%.

Not yet filed against `Blaizzy/mlx-vlm`. The module landed 2026-08-26 with two
commits and no third-party validation.

## Rejected approaches

Nine optimizations were measured and rejected. Each number is reproducible.

| Test | Rejection reason |
|---|---|
| Expert cache (3 designs) | 76.5% hit rate ran 4257 ms/token against 1390 with no cache |
| Resident slab, output merge | 65% hit rate, 35x slower; its RAM was worth more as page cache |
| Cache-warming prefetch | steals NVMe bandwidth: 907 MB/s at 16 readers, 615 at 32 |
| Bulk tensor reads | 208 s against 124.6 s on prefill |
| More than 16 IO workers | 32 workers took 212.9 s against 120.5 s |
| Repacking the checkpoint | the 1.84x was page-cache residency; controlled, the original wins |
| Requantizing experts to 2-bit | 71.9% output error; SiLU amplifies gate error 44% -> 67% |
| Low-rank experts | rank 64 holds 23.9% of energy, a random matrix holds 19.5% |
| Co-activation reordering | 2.17x collapses to 1.25x on held-out routing |
| Skipping MoE in weak layers | routed experts are 79.6% of output median, never below 42% |

The measurements show no exploitable redundancy in this 512-expert MoE with
auxiliary load-balancing loss. RAM allocation outside the page cache reduced
performance.

## Measurement controls

Concurrent model instances invalidated measurements. Two instances each ran
at 76% of solo speed. `bench_parallel.py` and the prompt-control driver counted
processes by executable path. A shell guard for `macqwen/session.py` matched its
own shell and failed.

A valid A/B used the same prompt. Prompt style alone changed throughput by 23%.

Thinking costs 3.7%. It is not a significant variable.

Run-to-run variance on an unchanged configuration reached 2x. The page cache
falsified six measurements during this work. Rules that survived:

- One model load can switch configurations inside one process.
- Separate processes require identical work before timing.
- Reversed or interleaved runs confirm each result.
- Changes below about 20% are inconclusive.
- Synthetic reads show 20 to 50 GB/s when the file is cached.
- The real model has a 45 GB expert pool and supplies the valid result.

## The physical bound

Each token activates 2.36B expert params (10 of 512, across 48 layers). Those
bytes must cross the SSD, which does ~1.07 GB/s on this gather pattern and
2.29 GB/s sequential.

```
bits/group   MB/token   tok/s at 1070 MB/s
4 / 32          1475          0.73     <- the shipped checkpoint
2 / 128          664          1.61     <- but 71.9% error, unusable
```

Exact routing fixes this byte count. Approximate routing can read fewer experts.

## Fast-quality profile

`--fast-quality` is the retained approximate quality-recovery profile.

1. The prompt and first eight output tokens use threshold 0.85.
2. Those eight tokens identify six experts with highest omitted route mass.
3. Their file-backed pages are pinned. This uses 0.93 GB without copying.
4. Later tokens use the fast thresholds and add any pinned top-10 experts.
5. Original router scores feed a 0.10 residual blend. Effective weights still
   differ from the normal profile.

The prompt alone predicts only 9.1% of omitted router mass. The first eight
output tokens predict 22.5%. A future-aware oracle reaches 33.5%.

On a 120-token Portuguese photosynthesis answer:

- plain fast: 2.07 tok/s and mixed Portuguese, Spanish, and English;
- fast-quality: 2.34 tok/s, 3.63 experts per layer, coherent Portuguese;
- 0.62 GB also preserves this photosynthesis answer, but measures 1.62 tok/s;
- a direct terminal control under a slower cache state measures 1.48 tok/s
  for fast and 1.31 tok/s for fast-quality, an 11% gap.

The speed difference is below the system's measured 20% variance. The quality
difference is large and repeats. Run it with:

```bash
./chat.sh --model flashnext --fast-quality
```

A 128-token Python test still exposes residual drift. H3 to H5 mix English
into Portuguese comments. Default H6 also emits `transform para minuscule`.
`--exact-quality` preserves the normal profile output.

## Exact-quality profile

`--exact-quality` keeps threshold 0.85, `pread`, scores, and all selected
experts unchanged. It changes only file-cache residency.

1. The first eight output tokens collect normal routed experts.
2. The eight experts with highest cumulative route mass per layer are selected.
3. Their weights, scales, and biases are pinned as file-backed pages.
4. The remaining generation continues with normal routing.

The pinned set uses 1.24 GB during generation. The chat releases it after each
answer.
Pinning takes about 0.23 seconds. Generated token IDs stay identical to the
normal threshold-0.85 profile.

Two post-warmup H8 runs measure 1.59 and 1.44 tok/s. Two controls measure
1.21 and 1.28 tok/s. The tail gain is 22%; it excludes warmup and pin time.
The result is provisional because it is close to the 20% system variance.
H6, H10, and H16 lose. A four-token warmup, global allocation, partial tensor
pinning, and `shared_mmap` also lose.

Run it with:

```bash
./chat.sh --model flashnext --exact-quality
```

## Exact persistent sessions

`macqwen/session.py` can now save and restore the complete text-generation
state. A restored session processes only the new turn. It does not replay the
old context.

```text
/salvar NAME
/carregar NAME
/sessoes
/apagar NAME
```

The single safetensors file includes all 36 DeltaNet states, 12 QSA caches,
QSA indexer data, PLE state, position state, consumed token IDs, and the
thinking mode of the saved conversation. It also contains checkpoint,
tokenizer, engine, and routing-profile fingerprints. Writes are private and
atomic. A SHA-256 checksum protects the payload. The default directory is
`~/.cache/flashnext/sessions`.

The real-model test extends a short cache to 2,052 synthetic QSA positions.
The extension activates sparse QSA without a long prefill. Its snapshot was
172.5 MB.
Restored logits and QSA auxiliary arrays had maximum difference 0. Hot-cache
save took 0.15 to 0.20 seconds. Load took 0.08 seconds. The layout was 36
`ArraysCache` plus 12 `QSAKVCache`.

A smaller prefiller cannot create an exact compatible cache. Every QSA,
DeltaNet, and PLE state depends on target-model activations. A trained state
predictor remains an approximate research path. Exact remote prefill remains
possible in principle. It needs a portable full-checkpoint identity and an
explicit import mode. The current implementation accepts only the local model
instance.

## Chat controls

The chat prints its command list at startup. `/ajuda` prints it again.

```text
/thinking on|off
/thinking show|hide
/max-tokens N|off
/status
```

Thinking activation and display are separate states. `/thinking on` changes
the prompt for the next turn. `/thinking hide` keeps reasoning active and
hides its contents. A positive reply limit prints a visible warning when hit.

Terminal input uses bracketed paste. Newlines inside a paste stay in one input
turn, including a trailing newline. Generation begins only after Enter is
pressed after the paste. Control markers inside a paste stay literal
text. The model context limit is 262,144 tokens.

## Closed and open conclusions

### Exact 3 tok/s blocker

The local non-quantized exact path is exhausted on this 16 GB machine.
Authoritative complete-chat evidence remains 1.9 tok/s for
`./chat.sh --model flashnext --exact-quality`. The 48-token perfect-draft oracle reaches 2.90
tok/s before any predictor cost. The real corrected MTP reaches only 1.6
tok/s in the same terminal flow.

The remaining changes that could plausibly cross 3 tok/s require at least one
constraint change:

- use a lower-bit checkpoint;
- allow a different greedy-token trajectory;
- move the model to hardware with more memory or faster effective storage.

The recorded success condition was a complete-chat A/B above 3.0 tok/s with
identical greedy token IDs.

Keep these conclusions:

- Keep the original `Vontra/Qwen3.8-Flash-Next-MLX-oQ4` checkpoint.
- Keep `exact-quality` as the default.
- Treat direct n-gram shard dispatch as unaccepted until a complete-chat A/B
  exceeds the 1.9 tok/s baseline with identical token IDs.
- Treat gains below 20% with caution unless reversed A/B runs repeat them.
- The Whallm 512-slot, 5,001-token prefill was closed on a 16 GB Mac.
- Expert caches, broad pinning, expert-major blobs, and draft paths were closed.
- Whallm modality removal was closed because its checkpoint was text-only.
- Affine bias reconstruction from scales was closed.

The following goals remain open:

- reach a controlled 3 tok/s while preserving exact greedy token IDs;
- reach 5 tok/s without the lexical damage from `--fast`;
- measure joules per token. `powermetrics` needs administrator access;
- run a longer quality session before committing the retained change.

## Chat input and session-state fixes on 2026-08-30

Two chat defects were found and fixed. Neither changes model weights, routing,
or the exact-quality trajectory. The 1.9 tok/s baseline is unaffected.

### Thinking mode broke saved conversations

`macqwen/session.py` built `session_profile` once at startup and put
`"think": bool(thinking_enabled)` inside it. `SessionStore` froze that
dictionary in the compatibility key. Two failures followed:

- `/thinking on` during a chat never updated the profile, so `/salvar`
  recorded the startup mode instead of the live mode;
- a snapshot saved under a different thinking state refused to load. The
  error was `sessão incompatível: perfil de geração diferente`.

The fix removed `think` from the compatibility profile. Thinking selects the
prompt format but does not change cache arithmetic. It no longer gates a load.
The manifest stores the mode as `thinking`.
`/salvar` stores the live mode, `/carregar` restores it, and `/sessoes` lists
it. `/carregar` does not change the display preference, because
`/thinking show|hide` stays a separate display preference.

Snapshots written before this change no longer load. The compatibility profile
changed. The current worktree already invalidated them through
`_engine_fingerprint`, which hashes `adaptive_topk.py`, `loader.py`, and
`store.py`.

### Pasted transcripts lost most of their text

A pasted transcript that carried `<think>`, `</think>`, or `<|im_end|>` reached
the model as chat structure. `macqwen/session.py` passed the complete turn string to
`tokenizer(text)`, and the tokenizer converted those strings into control
tokens 248068, 248069, and 248046. The pasted `<|im_end|>` closed the input
turn, so only the text before it stayed inside the turn. The model reported
that no earlier context existed.

The terminal reader was cleared first. A real pty test round-tripped bracketed
pastes of 77 B, 1.5 KB, 15 KB, and 61.6 KB with exact SHA-256 matches. The loss
was entirely in tokenization.

`build_user_encoder()` now splits input text around every added-token string.
It encodes each marker as its first character plus the rest, so the characters
survive and the control token never appears. The turn is built from a slot in
the rendered template, so only the input text takes this path. A prompt without
markers uses the previous whole-string call and stays byte-identical.

Verified against the real tokenizer: zero added-token IDs inside the input text,
exact character round trip, and only the 5 structural tokens of the template
in the complete turn.

Complete-chat check with `--think` and a marker-laden paste:

| Metric | Result |
|---|---|
| prompt tokens | 112, the complete paste |
| model reads the final line | yes |
| the end-of-turn marker in the reply | written as plain characters |
| exit code | 0 |

Before the fix the model saw only the first two lines. It now quotes the whole
paste and answers the final question.

## Large-prompt allocator release on 2026-08-30

The allocator release is the first accepted complete-chat gain in this
document. It applies only to prompts above 2,048 tokens. It changes no weight,
route, or arithmetic.

### Symptom

`./chat.sh --model flashnext --exact-quality` decoded at 1.5 tok/s after a 6,579-token prompt. The
same profile reaches 1.9 tok/s with a short prompt. The chat printed
`model 1.31 GB`, so the machine appeared to have free RAM.

### Cause

`prefill_language` has two branches. The branch for prompts at or below 2,048
tokens released its logits and called `mx.clear_cache()`. The branch above
2,048 tokens did not. MLX keeps freed buffers in its own allocator, so those
buffers stayed reserved for the complete decode.

Measured around a 4,096-token prefill:

```text
after load       active 3.304 GB   cache 0.000 GB   ps rss 0.91 GB
after prefill    active 3.584 GB   cache 7.564 GB   ps rss 0.83 GB
after clear      active 3.584 GB   cache 0.000 GB   ps rss 0.83 GB
```

MLX held 7.564 GB of unused buffers. On a 16 GB machine that RAM belongs to the
page cache of the 70 GB expert bank. `ps rss` does not count MLX Metal buffers,
so the chat display hid the whole effect.

### Fix

Drop the prefill output references, then call `mx.clear_cache()`. The token and
the cache state are already evaluated, so no value can change.
`FLASHNEXT_PREFILL_CLEAR_CACHE=0` restores the previous behaviour for A/B runs.

### Complete-chat A/B/B/A

One fresh process per run. Prompt 4,822 tokens, reply limit 40 tokens,
`--exact-quality`.

| Run | Decode | Tail | MLX cache at end | Token SHA-256 |
|---|---:|---:|---:|---|
| A release | 1.400 tok/s | 1.862 tok/s | 0.10 GB | `63e492a32f8931ed` |
| B keep | 0.730 tok/s | 1.205 tok/s | 8.80 GB | `63e492a32f8931ed` |
| B keep | 0.794 tok/s | 1.431 tok/s | 8.80 GB | `63e492a32f8931ed` |
| A release | 1.251 tok/s | 2.097 tok/s | 0.10 GB | `63e492a32f8931ed` |

| Metric | Keep | Release | Gain |
|---|---:|---:|---:|
| decode mean | 0.762 tok/s | 1.325 tok/s | +74.0% |
| tail mean | 1.318 tok/s | 1.980 tok/s | +50.2% |

All four runs produced the same token IDs. Both gains exceed the 20%
acceptance threshold. The released tail of 1.980 tok/s restores the short-prompt
baseline for a 4,822-token prompt.

### Two candidates rejected by measurement

The prompt-logits hypothesis no longer applies. Above 2,048 tokens the prefill
already uses `skip_logits=True` with a hidden-state argmax. `hidden_states`
holds one tensor of about 34 MB, not 2.48 GB.

QSA indexer recompute per decode token was isolated with the real dimensions
and no model load. `compress_ratio` is 4 and `block_topk` is 512, so the
indexer returns `None` below 2,049 keys:

| Context | Indexer cost, 12 QSA layers |
|---:|---:|
| 2,048 | 0.3 ms |
| 4,096 | 11.8 ms |
| 8,192 | 16.7 ms |
| 16,384 | 23.9 ms |

At 1.5 tok/s one token costs 667 ms, so an 8,192-token context spends 2.5%
there. An incremental pooled-key cache cannot repay its exactness risk.

### flash-moe comparison

Most transferable items from `danveloper/flash-moe` already appear as rejected
here: contiguous expert records are the expert-major blob, aligned
`newBufferWithBytesNoCopy` is the VM zero-copy test that fell to 0.065 tok/s,
`F_RDAHEAD` off is 13% slower, and route prediction with A/B buffers measured
1.11 tok/s. Its persistent four-worker I/O pool already exists in
`expert_cache.py` as a module-level `ThreadPoolExecutor`.

One item stayed untested. `expert_cache.py` called `mx.eval` per layer on new
expert rows. Flash-moe submitted expert work without an immediate wait. The
comments at `expert_cache.py:72` and `expert_cache.py:154` record the reason.

### Diagnostics added

`/status` now prints MLX active and cache memory next to RSS. The benchmark
JSON adds `mlx_active_gb`, `mlx_cache_gb`, and `mlx_peak_gb`. The per-turn
`model X GB` still reported `ps rss`. It did not report total memory.


## Complete decode token profile on 2026-08-30

The complete token profile replaces the model that guided earlier work. The
comment at `expert_cache.py:80` said decode is I/O bound at the drive's limit
and that reading fewer bytes is the only lever. Measurement says otherwise.

Run it with `FLASHNEXT_PROFILE_IO=1 models/flashnext/bench_decode_split.py
--profile-layers`. Add `--eval-layers` to force a sync inside each layer and
attribute the GPU drain; that perturbs the total but splits the buckets.

### Components of a 499 ms token

| Bucket | ms | Share |
|---|---:|---:|
| blocked on expert reads | 240.3 | 48% |
| GPU drain at `mx.eval(scores)` | 157.1 | 31% |
| `to_mx` host copy of 429 MB | 41.8 | 8% |
| GPU drain at `mx.eval(flat)` | 22.1 | 4% |
| final eval | 7.3 | 1% |
| n-gram reads | 6.1 | 1% |
| top-k Python loop | 3.5 | 1% |
| shared expert | 2.2 | 0% |
| MoE issue | 0.8 | 0% |
| unattributed | 17.8 | 4% |

Grouped: **SSD 246 ms, GPU 186 ms, host copies and Python 66 ms.**

Two facts correct the old model. The SSD delivers **1787 MB/s while reading**,
near the 1.97 GB/s this document records for the isolated reader, so bandwidth
is not the constraint. And there are **two host syncs per layer**, not one:
`mx.eval(scores)` in `adaptive_topk._moe_call` and `mx.eval(flat)` in
`expert_cache.build_plan`. Only the second was ever measured. Because MLX is
lazy, the first drains that layer's attention and GDN work, which is why the
MoE block appeared to hold 96% of a token.

### GPU work by owner

Measured with `--eval-layers`, inflated by roughly 10% from the added syncs.

| Component | ms/token | Layers | Per layer |
|---|---:|---:|---:|
| GatedDeltaNet | 56.9 | 36 | 1.58 |
| router, remaining in score sync | 35.7 | 48 | 0.74 |
| expert matmuls | 16.8 | 48 | 0.35 |
| QSA attention | 15.0 | 12 | 1.25 |
| PLE | 7.8 | 1 | 7.8 |
| hyper-connection | 2.8 | 96 | 0.03 |

There is no GPU hotspot. It is many small Metal dispatches across 48 layers.
`Fused GDN input projections` lost at 1.66 against 1.75 tok/s. It fused the
largest component but did not overcome dispatch overhead.

The top-k Python loop costs 3.5 ms. `to_mx` costs 41.8 ms. Neither matches the
size once assumed for them.

### SSD and GPU dependency chain

Each layer runs a strict chain:

```text
attention(N) -> router(N) -> read experts(N) -> matmul(N) -> attention(N+1)
```

The read cannot start before the router, and the router cannot run before that
layer's attention. So the two largest costs alternate by construction. Perfect
overlap would give about 306 ms, or 3.27 tok/s.

The dependency chain also explains two existing results. The shared-expert
`mx.async_eval` already in `_moe_call` wins only 2.2 ms, because the shared
expert is the sole GPU work that does not depend on the read. The block oracle reaches 2.90
tok/s because block verification breaks the chain, not because it computes
faster.

### The four routes to 3 tok/s

3.0 tok/s is 333 ms against 499 ms measured.

| Route | Mechanism | Ceiling | State |
|---|---|---:|---|
| 1. overlap SSD and GPU | fill the idle disk window | 3.27 tok/s | needs the chain broken |
| 2. cut the 186 ms GPU | no hotspot; dispatch bound | - | fusion already lost |
| 3. cut the 246 ms disk | about two thirds fewer bytes | - | lower-bit checkpoint |
| 4. cut the 42 ms `to_mx` | read into MLX-owned buffers | 8% alone | unexplored |

Route 4 is distinct from two rejected entries. `VM zero-copy experts` mapped
the checkpoint itself and `Reusable decode buffers` reused NumPy buffers with
`preadv`. Neither removed the main-thread copy that sits between the read
completing and the matmul being issued.

Note for route 1: `Cache-warming prefetch` was rejected because it steals NVMe
bandwidth. That reasoning assumed a saturated drive. The drive is now known to
be idle for about 37% of a token, so warming inside the GPU window spends idle
bandwidth rather than contended bandwidth. flash-moe's memory-controller
finding identified a risk that required measurement.


## All four routes, closed on 2026-08-30

| Route | Mechanism | Result |
|---|---|---|
| 1. overlap SSD and GPU | early submit, no prediction needed | **-8.2%**, memory-controller contention |
| 2. cut the 186 ms GPU | `mx.compile`, first attempt in this project | 3 to 4% ceiling; work is real |
| 3. cut the 246 ms of bytes | lower-bit checkpoint | untested; needs 86.152 GiB free |
| 4. cut the 42 ms host copy | shared read buffer | copy removed, token unchanged |

Routes 1, 2 and 4 are measured and closed. Every code-side lever on this
machine and this checkpoint is now exhausted with numbers rather than
argument. Route 3 remains, and it is a storage and quality decision.

Full evidence for each route is in `RESEARCH.md`.

In-process overlap is closed. Three mechanisms produced three losses, all
byte-exact: early submit -8.2%, shared read buffer absorbed by the GPU, warm
prefetch -15.4%. Two processes overlapping the same two units win 52%. The
difference is whose critical path the overlapped work sits on: inside one
process the I/O slows the exact GPU work the main thread already waits for,
and bought no independent progress. The single-instance prefetch, read-ahead,
and overlap paths were closed.

## Accepted on 2026-08-30: pin 32 resident experts

`--resident-experts` now defaults to 32, which pins 4.46 GB. This is the
second accepted change of the day.

### Invalid earlier measurements

`12 pinned experts per layer | 1.82 versus 1.84 tok/s | reject` and
`Pinning 1.85 GB is slower` were measured on a machine with **0.12 GB free**.
Pinning under that pressure evicts something else, so the test could only lose.

Measured during decode with other applications running:

```text
Pages free                      0.12 GB
Pages wired down                5.77 GB
File-backed pages               5.25 GB
Pages occupied by compressor    2.49 GB
```

After quitting Firefox, OneDrive and Activity Monitor, `Pages free` rose to
4.83 GB and the compressor fell to 0.80 GB. Physical reads dropped 7.4%, from
405 to 375 MB per token.

macOS then left 3.18 GB free while streaming 375 MB per token from the SSD.
File-backed cache grew only from 6.01 to 6.72 GB. The kernel did not promote
pages from large random reads on a 111 GB file. `pin_rows` claimed idle RAM.

### Sweep

Nine runs, three per configuration, ordered `8 24 32 / 32 24 8 / 8 24 32`,
56 tokens each with a 48-token pinned tail, `--exact-quality`.

| Resident | Pinned | Tail mean | Change | Spread | Runs |
|---:|---:|---:|---:|---:|---|
| 8 | 1.24 GB | 2.474 t/s | - | **0.304, 12%** | 2.432, 2.647, 2.343 |
| 24 | 3.67 GB | 2.568 t/s | +3.8% | 0.046, 1.8% | 2.588, 2.542, 2.574 |
| 32 | 4.46 GB | 2.583 t/s | +4.4% | 0.043, 1.7% | 2.586, 2.560, 2.604 |

All nine runs produced token SHA-256 `3cf08cfd22d0f64a...`.

### Read the result correctly

The mean gain is +4.4%, below the 20% acceptance threshold on its own. The
reason to accept it is the spread.

Pinning does not raise the ceiling. The best 8-expert run, 2.647 t/s, still
beats the best 32-expert run, 2.604. It removes the floor: the worst 8-expert
run is 2.343 and the worst 32-expert run is 2.560.

Run-to-run variance falls **7x**, from 12% to 1.7%. This document's own
"Measurement controls" section records 2x variance and at least three
findings reversed as page-cache artifacts. The project accepted the stable
floor because it improved later A/B tests. This also explains the non-monotonic
16-expert point seen in an
earlier two-sample sweep: that was the 8-expert configuration's variance, not
a real dip.

### Operating note

The gain required free RAM. Firefox left 0.12 GB free and made pinning compete
for memory. The 2.583 t/s result used a quiet machine, a short prompt, and a
48-token tail. Longer context and a busy desktop produced lower rates.
