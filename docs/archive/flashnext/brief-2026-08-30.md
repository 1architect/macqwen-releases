# Briefing: making a 176B MoE usable on a 16 GB Mac

The document records the investigation state on 2026-08-30. It covers the
hardware, constraints, measurements, rejected paths, and open questions.

## The machine and the model

```
Mac16,12 · Apple M4 · 16 GB unified memory · ~2.3 GB/s SSD
```

Qwen3.8-Flash-Next uses architecture `qwen4_exp` and was released 2026-08-26.

```
176B params total
  121B  routed MoE experts   (512 per layer, top-10, 48 layers)
   51B  hashed trigram embedding table (20M rows x 160 dims, 128 shards)
    4B  remaining tensors: attention, embeddings, vision tower, PLE, hyper-connections
```

48 layers = 36 Gated-DeltaNet (linear attention) + 12 full attention. Hidden
2560, `moe_intermediate` 640, vocab 248320, 262144 max context. Multimodal.

Checkpoint in use: `Vontra/Qwen3.8-Flash-Next-MLX-oQ4`, 111.7 GB, MLX
safetensors, 4-bit affine group-32 base with 228 per-tensor overrides at 5 and 8
bits. BF16 source is 360 GB and does not fit on the 228 GB disk.

## Streaming runtime

`flashnext/` kept the two large tensor families on the SSD. It read only the
data selected for each token.

```
store.py           np.memmap per tensor, MADV_RANDOM, row gathers in C
expert_cache.py    reads the routed experts per layer, 9 parallel reads
ngram.py           n-gram rows read per lookup instead of holding 19 GB
loader.py          swaps modules in before anything materializes
adaptive_topk.py   routes to as many experts as router confidence justifies
patch_rmsnorm.py   fixes an upstream correctness bug
```

Stock mlx-vlm materializes every weight: 24 GB of swap in two minutes, no token
produced. With `flashnext`: **4.19 GB resident, 2.1 s load**.

Every streaming module is bit-identical to the dense path (`max_diff = 0.0`)
from 1 to 800 tokens.

## Upstream RMSNorm fix

`mlx_vlm/models/qwen4_exp/language.py` applies `y * (1.0 + weight)` in
`Qwen4ExpRMSNorm`, with a comment claiming checkpoint weights are zero-centered.
Every norm family has a positive minimum:

```
norm_conv  mean +0.891 min +0.543    q/k_norm   mean +1.358 min +0.098
norm_key   mean +0.893 min +0.672    hc_norm    mean +3.750 min +0.633
```

The `1.0 +` doubles every norm's gain. No NaN, no overflow, so hidden states look
healthy layer by layer and the failure reads as fluent nonsense. Fixed:
"The capital of France is" → " Paris" at 44.4%; broken: punctuation at 3%.

## Performance measurements

```
                                          ms/token   tok/s
start                                         7960   0.126
np.memmap gathers (not per-row frombuffer)    5298   0.189
batched reads, LRU cache removed              2735   0.366
nine parallel reads per layer                 1840   0.543
16 IO workers                                 1788   0.559
restored index sorting                        1671   0.598
MADV_RANDOM + chunked gathers                 1390   0.719
adaptive top_k @ 0.85                        ~1060   0.94
```

Prefill is separate and worse: **93 tokens in ~120 s**, because a MoE prefill
routes ~290 distinct experts per layer against decode's 10, reading 25.35 GB.

## Hardware limit

Each token activates 2.36B expert params (10 of 512 × 48 layers × 3 projections
× 640×2560). Those bytes must cross the SSD.

```
per token          1475 MB
gather throughput  1068 MB/s   (sequential dd measures 2292 MB/s)
pure I/O           1381 ms
measured           1390 ms
```

The 48 host syncs that routing forces cost **8 ms total**. `gather_qmm` costs
3.2 s of a 121 s prefill. **The GPU is idle. This is pure I/O.**

## Rejected paths and measurements

| Test | Result |
|---|---|
| Expert LRU cache (3 designs) | 76.5% hit rate, **4257 ms/token** vs 1390 with no cache |
| Resident slab, output-side merge | 65% hit rate, **35x slower**; slab RAM is worth more as page cache |
| Cache-warming prefetch | 1870 vs 1840 ms; NVMe bandwidth is scarce, not parallelism |
| Bulk tensor reads (prefill) | 208 s vs 124.6 s |
| More IO workers | 16 is peak; 32 workers took 212.9 s vs 120.5 s |
| Repacking checkpoint layout | apparent 1.84x was page-cache residency; fair test shows repack *slower* |
| Requantize experts to 2-bit | **71.9% output error** (SiLU amplifies gate 44% → h 67%) |
| Low-rank expert approximation | rank-64 holds 23.9% of energy; a *random* matrix holds 19.5% |
| Low-rank predictor for active units | 21% recall of true top-128 vs **20% by chance** |
| Expert co-activation reordering | 2.17x collapsed to **1.25x** on held-out data |
| Skip MoE in low-impact layers | median routed contribution is 79.6%, minimum 42.6% |
| Skip biases | not a symmetric-quant artifact: std 0.035, 0% zeros |
| `MADV_WILLNEED` | 1.5x slower |

## Design constraints

1. **Routed expert sets never repeat between tokens.** 0% exact over 480
   samples; 35.7% pairwise overlap. No whole-result cache can hit.
2. **Expert usage is Zipfian but caching still loses.** 19% of experts resident
   gives 76% hit rate. The merge cost caused the failure.
   Merging weights with `mx.stack` leaves lazy nodes; with `np.stack` the cached
   rows are views that pin whole read chunks.
3. **Experts are full-rank.** `router_aux_loss_coef` makes experts different and
   uses their full capacity. The measurements found no compression margin.
4. **Intra-expert sparsity is real but unpredictable.** 40% of the 640
   intermediate units hold 96.2% of energy. The median unit is 4.5% of its row
   maximum. No cheap method predicts *which* 40%, because `h = silu(gate)·up` depends on
   two full-rank matrices.
5. **`silu(gate)` alone can gate skipping** (97.1% energy keeping 60% of units)
   but `down_proj` stores its 640 inputs packed 8-per-uint32, so column slicing
   is bit-unaligned. Only `up` can be skipped → 1.15x, not worth two-phase reads.
6. **RAM spent on anything but page cache is wasted.** This explains every cache
   failure above.

## Retained result and mechanism

Adaptive top-k takes experts until the router's cumulative probability passes
a threshold. At 0.85 mean k drops only ~12%, but decode runs **1.8x faster**
(1900 → 1060 ms), confirmed in both sweep directions.

The extra factor is a **page-cache cliff**. A smaller routed set means a smaller
working set, and crossing below ~8 GB of usable cache produces a
super-linear jump. The cliff sits between thresholds 0.90 and 0.85; below 0.85
the curve flattens again because the cache benefit is already collected.

Quality holds: at threshold 0.70 the greedy output is **byte-identical** to
threshold 1.0 on tested prompts, unlike fixed `top_k=6` which breaks arithmetic.
Adaptive keeps all 10 experts when the router is uncertain.

## Measurement rules

Run-to-run variance on an unchanged config reached **2x** (1390 to 2920
ms/token). The page cache falsified **seven** measurements in this work, in both
directions: it inflated false gains (repack, sequential reads, two layout
benchmarks) and it *hid* a real gain (threshold sweep, where quality-check
prefills flooded the cache before timing).

Rules that emerged:
- Only differences above ~20% are meaningful.
- Every result needs a control: reversed order, interleaved rounds, or held-out
  data. Two tests could have caused destructive 111 GB rebuilds without one.
- Never run two benchmarks concurrently. That invalidated one comparison here.
- `np.ascontiguousarray` returns a view for an already-contiguous memmap slice.
  This can produce a false 400 GB/s result.
- Build and evaluate an ordering on separate samples.

## Open questions

1. **Prefill.** 25.35 GB for 93 tokens. Chunking is worse, not better (16-token
   chunks would read 69 GB total). GPU idle. Nothing tried has helped.
2. **Per-layer thresholds.** Routed contribution varies 42% to 87% across layers. A
   global threshold treats them alike. Untested.
3. **Reading efficiency.** Sequential reads reach 2292 MB/s. Gathers reach
   1068 MB/s.
   The gap is real but repacking did not capture it. `preadv` scatter-gather
   instead of mmap page faults is untested.
4. **Freeing resident RAM for page cache.** The vision tower uses about 1.5 GB
   of the 4.19 GB resident set. Text-only use does not need it. Concurrent runs
   invalidated one test. A controlled repeat remained open.
5. **`F_NOCACHE` on n-gram reads.** They cost 0.2 s but their pages evict expert
   pages that would be reused.

## Measured bound

To reach 3 tok/s, the runtime needs 333 ms/token and four times fewer bytes. Requantization is
the only lever with that magnitude and it produces 72% output error. A 512-expert
MoE with auxiliary-loss balancing is *designed* to have no exploitable
redundancy. The realistic ceiling on this hardware is about 1 to 1.5 tok/s.

The acceptance rule required fewer bytes per token and a page-cache control.
